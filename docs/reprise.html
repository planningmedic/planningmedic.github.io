1Ce que c'est

Portail web du service d'anesthésie du service (~23 MARs) : gardes à l'année avec algorithme d'équité, planning quotidien, consultations, portail personnel, module libéral, veille bibliographique. Aucune donnée patient.

Le système a été conçu et maintenu par une seule personne, sans bagage de développement, en dialoguant avec une IA. C'est reproductible : voir le chapitre 5.

Deux comptes Google distincts, à ne pas confondre : planningmedic (compte de service, porteur du classeur, du code serveur et des JSON publiés) et le compte personnel du mainteneur, qui ne sert qu'à tirer la sauvegarde hebdomadaire (chapitre 3).

Le risque principal

Tout ce qui fait tourner le système dépend du seul compte planningmedic. S'il devient inaccessible, le système continue de tourner, mais plus personne ne peut le modifier ni le réparer.

Mesures de continuité — dix minutes, tant que c'est possible

  1. Ajouter un second propriétaire à l'organisation GitHub planningmedic.
  2. Partager le classeur Sheets et le projet Apps Script avec un second compte de confiance, en droits d'édition.
  3. S'assurer qu'au moins une autre personne du comité connaît le code admin et sait où le retrouver (onglet CONFIG).
Un transfert de propriété ne s'improvise pas

Transférer complètement le projet Apps Script oblige à redéployer la Web App, ce qui change son adresse. Cette adresse est écrite en dur dans neuf fichiers du dépôt : les huit pages du site et l'estimateur libéral. Toutes devraient être mises à jour dans la foulée, sinon plus rien ne fonctionne. À planifier, jamais dans l'urgence.

3Sauvegarde des données

Le code est sauvegardé par GitHub, avec tout son historique. Les données le sont par deux sauvegardes automatiques et indépendantes — plus rien de manuel.

QuandQuoiOùPropriétaire
Lundi ~4 hbackupHebdo() copie le classeur maître, rotation sur 8 copiesDossier Drive Planning-Med-BackupsCompte planningmedic
Dimanche ~5 hScript indépendant qui va chercher une copie du classeur, rotation sur 8 copiesDossier Sauvegardes Planning-MedCompte personnel du mainteneur

La première protège de la fausse manœuvre — un onglet effacé, des données écrasées. Elle ne protège pas d'un compte perdu ou suspendu : l'original et les huit copies partiraient ensemble.

La seconde est là pour ça. Sur Drive, un fichier appartient à celui qui le crée : la copie étant tirée par un autre compte, rien de ce qui arrive à planningmedic ne peut l'atteindre. Le classeur est partagé en lecture seule — et une copie tirée depuis un partage en lecture emporte bien le script attaché (vérifié le 26/07/2026).

Ce qui reste manuel — une vérification par trimestre

Les 1er octobre, janvier, avril et juillet : ouvrir le dossier Sauvegardes Planning-Med du compte personnel, confirmer qu'une copie récente existe et qu'elle s'ouvre. Une sauvegarde jamais ouverte n'est pas une sauvegarde.

Installation, code du script, piège des comptes multiples dans le navigateur et procédure de restauration complète : docs/sauvegarde-compte-perso.md.

La limite qui subsiste. Ces deux sauvegardes protègent des accidents de données et de la perte du compte de service. Elles ne protègent pas de l'indisponibilité du mainteneur : ses deux comptes sont alors hors d'atteinte en même temps. C'est exactement ce que couvrent les mesures du chapitre 2.

4Les trois règles d'or

  1. Le dépôt GitHub fait foi. Tout le code y est, y compris l'Apps Script. Ne jamais modifier un .gs directement dans l'éditeur Apps Script sans le reporter dans le dépôt : la modification serait écrasée à la prochaine recopie.
  2. Une modification du code serveur ne prend effet qu'après recopie et nouvelle version de déploiement. Sans nouvelle version, l'ancien code continue de tourner — et le symptôme est déroutant : la correction semble sans effet.
  3. Ne jamais régénérer une année déjà générée. Le planning et sa preuve d'équité seraient détruits. Un garde-fou le bloque : ne pas le contourner.

5Reprendre la main — le premier jour

  1. Obtenir l'accès au compte Google titulaire ; vérifier l'ouverture du classeur et de l'éditeur Apps Script.
  2. Se faire ajouter à l'organisation GitHub planningmedic.
  3. Ouvrir admin.html avec le code admin → onglet Maintenance → 🔍 Diagnostic système. Il audite le classeur, GitHub, les JSON du Drive et la concordance des versions de code. Tout doit être vert.
  4. Lire guide-technique.html (la référence), puis guide-comite.html (usage comité) et guide-mar.html (usage MAR).

Faire évoluer le système sans être développeur

La méthode qui a fonctionné : créer un projet sur claude.ai, y joindre CONTEXTE-Planning-Med.md et ROADMAP-Planning-Med.md, fournir un jeton GitHub en début de session — à révoquer ensuite — et exiger systématiquement trois choses : vérification de l'état réel du dépôt avant toute modification, patch expliqué AVANT/APRÈS, et validation explicite avant chaque mise en ligne.

7À ne surtout pas faire

  • Supprimer ou renommer un onglet du classeur — tout le code s'y réfère par son nom exact.
  • Modifier du code serveur en production sans le reporter dans le dépôt.
  • Régénérer une année de gardes déjà générée.
  • Communiquer le code admin en dehors du comité.
  • Laisser traîner un jeton GitHub dans un fichier, un commit ou un message.

La version courte de ces interdits, écrite pour le comité en situation d'incident, est au chapitre 4 de si-ca-tombe.html.

8Réparations

Quatre avaries sérieuses et ce qu'on peut faire. Les trois premières se réparent ; la quatrième impose de s'arrêter.

8.1 · Des données ont disparu du classeur

Un onglet vidé, des lignes effacées, une colonne écrasée. Deux recours, dans cet ordre :

  1. L'historique des versions du classeur (Fichier → Historique des versions → Afficher l'historique). Google conserve les états successifs : on retrouve celui d'avant l'accident et on restaure. C'est le recours le plus rapide et le plus sûr, et il ne demande aucune compétence technique.
  2. Les sauvegardes du chapitre 3, si l'accident est trop ancien pour l'historique. Ne jamais restaurer par-dessus l'original : ouvrir la copie à côté et reprendre ce qui manque.

8.2 · Une année a été archivée par erreur

La clôture déplace quatre onglets vers le classeur d'archive et les supprime du classeur maître : GARDES_{année}, INDISPOS_{année}, AFFECTATIONS_{année}, STATS_GARDES_{année}. Rien n'est perdu, tout est reconstructible :

  1. Depuis le classeur d'archive, recopier les quatre onglets dans le classeur maître, avec exactement les mêmes noms.
  2. Dans CONFIG, remettre ANNEE_ACTIVE sur l'année restaurée.
  3. Rétablir INDISPOS_ACTIVE si la campagne de saisie était ouverte — la clôture supprime cette ligne.
  4. Dans HISTORIQUE, supprimer les lignes ajoutées par la clôture pour cette année.
  5. Le point qu'on oublie : la clôture purge aussi PLANNING_OVERRIDES de toutes les lignes de l'année et des précédentes. Ces modifications-là ne reviennent pas avec les onglets : il faut les reprendre depuis une sauvegarde (chapitre 3) ou les ressaisir.

8.3 · Le serveur ne répond plus, ou répond « Action inconnue »

Ce message a presque toujours la même cause : le code déployé ne correspond pas au code du dépôt. Soit une recopie a été oubliée, soit le déploiement n'a pas été mis à jour après la recopie.

  1. Onglet Maintenance → 🔍 Diagnostic système : il compare les versions du dépôt et celles réellement déployées, et signale les décalages.
  2. Recopier dans l'éditeur Apps Script les fichiers signalés, depuis le dossier gas/ du dépôt.
  3. Déployer une nouvelle version de la Web App. Sans cette étape, l'ancien code continue de tourner.
Ne pas confondre avec une panne

Si toutes les pages sont muettes alors que le classeur s'ouvre normalement, ce n'est pas le code : c'est l'accès au compte ou le déploiement lui-même. Voir 8.4.

8.4 · Le compte Google est inaccessible

C'est la seule avarie qu'on ne répare pas depuis l'interface. Ce qu'il faut savoir, dans l'ordre :

  • Les données ne sont pas perdues. La sauvegarde tirée par le compte personnel (chapitre 3) est indépendante et appartient à un autre compte.
  • Le code n'est pas perdu. Le dépôt GitHub contient 100 % du système, serveur compris.
  • Le service peut tourner en mode dégradé à partir d'une sauvegarde du classeur, ouverte à la main : voir si-ca-tombe.html.
  • Remettre le système en ligne suppose de repartir d'une copie du classeur, de redéployer la Web App depuis ce nouveau classeur, puis de reporter la nouvelle adresse dans les neuf fichiers du dépôt qui la contiennent. C'est un chantier de quelques heures pour quelqu'un qui code, pas un geste d'urgence.
À ne pas faire dans la panique

Ne pas créer un nouveau classeur « propre » et y recopier des données à la main. Toute la valeur est dans la structure des onglets, que le code connaît par cœur. Repartir d'une copie d'une sauvegarde, jamais d'une feuille blanche.
