A1Vue d'ensemble : quatre étages, trois chemins

En 2 minutes

Le portail est construit sur quatre étages : en haut, les pages que tout le monde voit ; en bas, les données. Entre les deux, deux intermédiaires — un relais très rapide pour lire, et le serveur Google, seul autorisé à écrire. Trois chemins relient ces étages : lire (par le relais, quasi instantané), agir quand on est le comité (les ordres partent dans une boîte aux lettres et sont exécutés dans la minute), et le chemin direct vers le serveur Google — plus lent, mais toujours là, et c'est lui qui a le dernier mot.

Les trois chemins, racontés pas à pas

1 · Lire (ouvrir une page). La page envoie une seule demande au relais Cloudflare, avec le code d'accès. Le relais reconnaît le code par son empreinte, applique les droits de la personne, et renvoie tout ce qu'il faut pour afficher — le tout en une fraction de seconde. Si quoi que ce soit cloche (relais en panne, donnée manquante, code refusé), la page bascule discrètement sur le chemin direct vers le serveur Google : plus lent, mais complet. C'est toujours le serveur qui juge en dernier ressort si un code est valable.

2 · Agir quand on est le comité (placer quelqu'un, poser un statut du jour, publier). Plutôt que d'attendre le serveur Google — qui peut mettre plusieurs secondes, voire se faire attendre les mauvais matins — la page d'administration dépose une fiche d'intention dans la boîte aux lettres du relais. Le dépôt prend une fraction de seconde et la fiche est en sécurité. Le serveur relève la boîte chaque minute et exécute les fiches dans l'ordre. Détails au §A6.

3 · Tout le reste passe en direct par le serveur Google : la saisie des indisponibilités, les réglages de l'équipe, les assistants annuels… La page envoie sa demande, le serveur vérifie les droits, écrit dans le classeur, répond. Dans la foulée, il note quelles copies du relais sont à rafraîchir : elles le sont dans la minute, et un grand rangement automatique, une fois par heure, rattrape tout ce qui aurait pu être manqué.

Pourquoi ces détours ? Les mesures qui les ont imposés

Tout part d'un constat mesuré (03/08/2026) : chaque demande au serveur Google coûte 2,5 à 5 secondes, quel que soit le travail réellement demandé. Google recompile tout le programme à chaque demande (~1,5 s, très stable), y ajoute du transport et une file d'attente. Autrement dit : environ 3 secondes de péage fixe avant que la première ligne utile ne s'exécute — et des pannes passagères aléatoires en prime.

Impossible, dans ces conditions, d'avoir des pages qui s'ouvrent vite. La solution a été de sortir le serveur Google du chemin de lecture (le relais, mis en place le 04/08), puis du chemin des gestes du comité (le journal, le 05/08). Le serveur Google garde l'exclusivité de l'écriture : c'est ce qui garantit qu'une seule autorité tient les données.

A2Le dépôt : là où vit tout le code

En 2 minutes

Le dépôt planningmedic/planningmedic.github.io contient 100 % du code — les pages du site comme les dix fichiers du serveur. Il est public : n'importe qui peut le lire, personne d'autre ne peut y écrire. Le site est servi directement depuis le dépôt : pousser une page, c'est la mettre en ligne. Public, donc : ce qu'on n'y met jamais

On n'y écrit donc jamais : un montant, un pourcentage individuel, un code d'accès, un mot de passe, un nom associé à l'un de ces éléments. Ce que le public peut voir : le code, les guides, et les noms de l'équipe — qui figurent déjà dans l'annuaire du service. Aucune absence, aucune coordonnée, aucune donnée de patient.

A3Le serveur Google : dix fichiers qui se partagent le travail

En 2 minutes

Le serveur est un programme attaché au classeur maître, mis en service comme « application web » : les pages lui parlent par internet, jamais directement au classeur. Son code est réparti en dix fichiers, chacun avec un rôle précis — plus un onzième morceau, le « module partagé », présent à l'identique côté serveur et côté pages. Le diagnostic de la page d'administration vérifie en permanence que les fichiers en service sont bien ceux du dépôt.

L'onzième morceau, le module partagé, contient la logique qui classe les MARs disponibles pour une case du planning — la plus sensible du poste comité. Elle n'est écrite qu'une fois, et recopiée à l'identique des deux côtés : c'est ce qui rend toute divergence impossible (§A5).

Le symptôme qui trahit une recopie incomplète — un message « Action inconnue » ou « fonction introuvable » après une mise à jour du serveur signifie presque toujours qu'un des dix fichiers n'a pas été recopié, ou que le dépôt était incomplet. Le dépôt doit toujours refléter la totalité du code en service, et réciproquement.

Comment une demande est traitée : droits et rôles

Chaque demande porte le code d'accès de la personne et le nom de l'action demandée. Le serveur reconnaît trois rôles : admin (le comité — accès à tout), MAR (lecture de son périmètre, saisie de ses propres indisponibilités — impossible d'atteindre celles d'un collègue), et secrétariat (deux actions seulement, tout le reste refusé d'office — §C4). Les actions sensibles — tout ce qui écrit pour tout le monde, tout le cycle annuel — refusent quiconque n'est pas admin.

Repères techniques

Environnement : Google Apps Script, déployé en Web App (adresse en /exec). Points d'entrée : doGet/doPost, qui confient tout au routeur _routeRequete_ (dans Indispos.gs). Rôles issus de checkCode ; refus des non-admins par _deny(). Chaque fichier poussé incrémente sa constante GAS_VERSION_* (format AAAA-MM-JJ.N) — c'est elle que le diagnostic compare au dépôt (contrôle de dérive, 9 fichiers : les 8 de gas/ + le module partagé partage/dispo_jour.js). Fonction endormie : setupAnnee (setup_annee.gs) n'est plus appelée par personne — la création des onglets de l'année suivante passe par initYear.

Trois lieux de stockage, trois statuts. Le classeur maître : toutes les données vivantes, la référence absolue. Le Drive privé : le planning publié et les archives — c'est lui que lisent les pages des MARs, pas le dépôt. Les copies chez Cloudflare : de simples doubles de lecture, refabricables à volonté. Le détail onglet par onglet du classeur a son propre guide (guide-fichier-maitre.html) — il n'est pas recopié ici, deux inventaires finiraient par se contredire.

A5Le relais Cloudflare : pourquoi les pages s'ouvrent vite

En 2 minutes

Le serveur Google reste le seul à écrire. Mais après chaque écriture réussie, il dépose une copie fraîche des données concernées chez Cloudflare, qui les sert aux pages en une fraction de seconde. Deux filets garantissent la fraîcheur : un dépôt de copies dans la minute qui suit chaque écriture, et un grand rangement complet toutes les heures. Et une trouvaille de plus : le panneau qui liste les MARs disponibles pour une case s'affiche sans aucun appel — il est calculé sur place, dans le navigateur, par le module partagé ; le serveur vérifie derrière, en silence.

Le serveur Google écrit
une action du portail vient de modifier le classeur ou le Drive
▼ il note ce qui devra être recopié, et répond tout de suite à la page
La minute suivante
un automate dépose les copies fraîches chez Cloudflare
▼ et chaque heure, un grand rangement recopie tout — même ce qui a été modifié à la main dans le classeur
Le relais Cloudflare
sert ces copies aux pages en ~0,15 s, après avoir vérifié l'empreinte du code d'accès et appliqué les droits de chacun
Une page qui vient d'écrire relit toujours le serveur en direct — jamais sa propre copie, qui pourrait avoir une minute de retard.
Ce que chacun peut lire au relais

Le relais applique les mêmes droits que le serveur. Un MAR y lit les années, les secteurs, le planning, les affectations — et ses indisponibilités à lui seul (le tri est fait par le relais). L'admin lit tout, y compris les données de pilotage (gardes, statistiques, compteur de mails, déclarations libérales du jour). Le secrétariat ne lit rien du tout au relais : sa seule porte est le serveur, avec deux actions. Les contenus des tuiles du portail (topos, staffs, veille, protocoles, annuaire) ne sont rafraîchis que par le rangement horaire — assumé, ils changent rarement.

Deux principes de fraîcheur, appris en exploitation : la page qui vient d'écrire relit le circuit direct ; et les écrans d'édition du comité évitent le relais pendant la minute et demie qui suit une écriture du planning — un éditeur ne doit jamais afficher du périmé.

Le panneau instantané — une seule logique, deux emplacements

Classer les MARs disponibles pour une case (qui est libre, qui est de garde, qui est du secteur…) est la logique la plus sensible du poste comité. La réécrire une seconde fois pour le navigateur aurait créé un risque de divergence sournoise — refusé. La solution : elle n'est écrite qu'une fois, dans le module partagé, et ce même fichier est embarqué tel quel des deux côtés — par les pages, et par le serveur.

Résultat : la page d'administration calcule chaque panneau sur place, immédiatement, à partir des copies du relais. Le serveur refait le même calcul de son côté et compare en silence : en cas d'écart (jamais vu depuis la mise en place), il corrige l'écran aussitôt et le signale dans la console du navigateur. Toute évolution de cette logique se fait dans le module partagé et se met en ligne des deux côtés dans la même livraison.

L'exploitation courante : pannes, codes, ménage
  • Panne de Cloudflare : rien à faire. Les pages basculent seules sur le serveur Google — le portail est juste lent le temps de la panne.
  • Changer ou retirer un code d'accès : le modifier dans le classeur (onglet MEDECINS, ou CONFIG pour l'admin), puis lancer le grand rangement pour que le relais l'apprenne tout de suite — sinon il l'apprendra à l'heure suivante.
  • Vider le relais : sans danger — le prochain rangement refabrique tout.
  • Après la démonstration du 4 septembre : vérifier que les copies de l'année fictive 2027 ont bien disparu du relais.
Repères techniques

Le relais est un « Worker » Cloudflare nommé miroir, code dans cloudflare/worker.js, stockage de copies « KV ». Deux guichets : /push (dépôt par le serveur, sur présentation d'un jeton secret — rangé dans les propriétés du script et les secrets du Worker, jamais dans le dépôt) et /read (lecture par les pages, via l'empreinte SHA-256 du code d'accès — les codes en clair ne quittent jamais Google, et celui du secrétariat n'est même pas déposé en empreinte). La liste des copies autorisées est verrouillée des deux côtés (CLE_VALIDE) — garde-fou contre les fautes de frappe. La table « quelle écriture rafraîchit quelles copies » s'appelle MIROIR_APRES_ECRITURE (miroir.gs) ; principe : recopier un peu trop large plutôt que trop étroit. Le grand rangement : miroirSyncComplet (déclencheur horaire, installé par miroirInstallerDeclencheur). Envoi différentiel (20/08/2026) : le serveur retient l'empreinte de chaque copie déposée et ne redépose que ce qui a réellement changé — les plafonds gratuits de Cloudflare sont de 1 000 écritures par jour, et le grand rangement les consommait à lui seul en renvoyant ses ~29 copies vingt-quatre fois. Les empreintes sont oubliées au passage de 4 h : une fois par nuit, tout repart sans condition. Si une copie semble figée sur une vieille valeur, lancer miroirOublierEmpreintes puis miroirSyncComplet. La garde anti-périmé des écrans d'édition : 90 secondes (_tsEcriturePlanning). Le module partagé : partage/dispo_jour.js, répliqué dans le fichier serveur dispo_jour ; le témoin de comparaison s'affiche en console sous [DISPO-TEMOIN]. Diagnostic rapide : ouvrir l'adresse racine du Worker (elle répond {"ok":true, "service":"miroir …"} avec sa version), et la commande chrono() (§C11) détaille chaque lecture. Drapeau de la file (20/08/2026) : /ecrire pose la clé jsignal en même temps que la fiche ; /tirer la lit et n'ouvre la file (KV.list, plafond gratuit 1 000/jour contre 1 440 passages) que si elle existe — ou une minute sur trois, filet contre une lecture périmée. Le drapeau est baissé AVANT l'ouverture, jamais après : une fiche arrivée pendant l'ouverture relève le drapeau et sera vue au passage suivant. {forcer:true} ouvre la file sans attendre. Aucun changement côté Apps Script : la réponse de /tirer garde la même forme.

A6Le journal d'intentions : pourquoi les gestes du comité sont instantanés

En 2 minutes

Avant : chaque geste du comité attendait la réponse du serveur Google — plusieurs secondes au mieux, parfois trente les mauvais matins, avec des échecs aléatoires. Depuis le 05/08/2026, le geste est déposé en une fraction de seconde dans une boîte aux lettres chez Cloudflare, avec accusé de réception ; le serveur relève la boîte chaque minute et exécute les fiches dans l'ordre. Depuis le 20/08/2026, déposer une fiche lève un drapeau : le serveur regarde le drapeau — un geste cent fois moins coûteux — et n'ouvre la boîte que s'il est levé, plus une fois toutes les trois minutes par sécurité. Rien ne change à l'usage : le geste passe toujours dans la minute. Trois types de fiches existent : les placements, les statuts du jour, la publication. L'écriture dans le classeur reste la seule vérité — la boîte n'est qu'une file d'attente fiable devant elle.

A7Sécurité & confidentialité : ce qui est protégé, et comment

En 2 minutes

Le principe directeur : tout ce qui est nominatif et sensible est verrouillé côté serveur ; ce qui est visible publiquement ne contient rien qu'on ne trouve déjà ailleurs. Deux mondes bien séparés (le dépôt public / les comptes Google privés), trois rôles où tout est refusé par défaut, aucun secret dans le dépôt, une « liste rouge » de données qui ne passent jamais par Cloudflare — et des limites assumées, listées honnêtement plutôt que cachées.

Les deux mondes
MondeQui peut voirCe qu'il contient
Le dépôt et le site🌐 Tout le mondeLe code, les guides, les noms de l'équipe (déjà publics via l'annuaire du service). Aucune absence, aucune coordonnée, aucune donnée de patient.
Le classeur et le Drive🔒 Le compte du projet, protégé par la double authentificationLe vrai référentiel : codes d'accès, emails, quotités, indisponibilités, gardes, planning publié, archives, relevé libéral.

La frontière est nette : les pages publiques ne contiennent aucune donnée sensible en dur. Elles ne les obtiennent qu'en présentant un code d'accès valide, et la réponse vient des données privées. Un visiteur du dépôt voit le mécanisme, pas ce qu'il manipule.

Les codes d'accès : comment ils protègent
  • Sans code valide, le serveur ne répond rien d'utile — toutes les actions sont derrière cette porte (une seule exception, anodine : la question « quelle est l'année active ? »).
  • Les majuscules/minuscules ne comptent pas (depuis le 27/07/2026). Le piège était invisible : sur téléphone, le champ met tout seul le code en capitales ; sur ordinateur non. Le même code passait sur mobile et échouait sur PC — incompréhensible pour la personne, indiagnosticable à distance.
  • Un MAR ne peut lire et écrire que son périmètre : la demande a beau viser un collègue, le serveur la ramène d'office à l'identité du code présenté.
  • Les codes ne redescendent jamais vers le navigateur : les écrans savent seulement si un code existe, jamais lequel. Et un code laissé vide dans un formulaire vaut « inchangé » — impossible d'effacer un code par accident.
  • Chez Cloudflare, seuls des empreintes circulent (§ lexique) — et celle du secrétariat n'y est même pas.
La liste rouge : ce qui ne passe jamais par Cloudflare

Le relevé libéral, les marges, les onglets CONFIG et PARAMETRES, la boîte mail, les journaux internes : rien de tout cela n'est copié chez Cloudflare. C'est un choix assumé, avec son prix — la page des consultations à venir, qui touche à ces données, plafonne à 4-5 secondes d'ouverture au lieu de 2 : la confidentialité passe avant la vitesse. Les secrets du projet (le jeton GitHub, la clé du générateur de comptes rendus) vivent dans l'onglet CONFIG du classeur privé, jamais dans le code. L'onglet PARAMETRES contient des secrets : on ne le cite jamais, on ne le recopie jamais.

Le générateur de comptes rendus : la seule sortie de texte clinique

C'est le seul endroit du système où du texte clinique quitte l'environnement Google — vers le service en ligne de la société Anthropic (hors Union européenne), pour aider à la rédaction. Cinq garde-fous superposés : l'accès est limité à une liste nominative ; le bouton reste gris tant que la case « texte anonymisé » n'est pas cochée, et le serveur refuse sans cette confirmation ; un filtre bloque l'envoi si le texte contient un signal d'identité clair (« né(e) le », numéro de dossier, civilité + NOM…) ; le modèle lui-même a pour consigne de refuser si un identifiant subsiste ; et la traçabilité ne conserve que l'événement, jamais le texte. Point encore ouvert : étudier une option sans conservation des données ou hébergée en Europe, à porter avec le référent RGPD du service.

Les limites assumées
  • Le dépôt public montre les noms de l'équipe et les objectifs de gardes de chacun — jugé acceptable, ces informations étant déjà accessibles par ailleurs.
  • Les codes des MARs sont lisibles en clair dans le classeur (protégés par l'accès au compte, pas par un chiffrement). Leur format rend le forçage par essais successifs impraticable, mais le code admin doit rester un code fort.
  • Le générateur de comptes rendus repose sur une discipline d'anonymisation outillée, pas sur une impossibilité technique de coller un identifiant.

La règle apprise en réel contre l'injection de code : tout texte saisi librement par quelqu'un (un motif, un message, un nom de patient) est neutralisé avant d'être affiché dans une page — une faille de ce type a été trouvée et corrigée dans le volet libéral. Les corps des mails, eux, sont affichés comme du texte pur, jamais interprétés (§C5).

Repères techniques

Vérification du code : checkCode (comparaison en majuscules, code vide refusé d'emblée). Cloisonnement MAR : le serveur force targetId = user.id. Journaux : CONNEXIONS (qui s'est connecté, purge au-delà de 2 000 lignes) et LOGS (événements techniques, purge au-delà de 500) — aucun ne contient de motif d'absence ni de donnée patient. Comptes rendus : action genererCRH (portail.gs), droit lu dans CONFIG / TUILES_PRIVEES, confirmation confirmAnonyme:true, filtre detecteIdentifiant(), clé ANTHROPIC_TOKEN dans CONFIG. Neutralisation d'affichage : _escHtml ; corps de mails posés en textContent. Empreintes : SHA-256, copie acces du relais.

En 2 minutes

Où s'arrêter pour un essai. Les quatre actions techniques — périodes, groupes, création de l'onglet, ouverture de la campagne — tiennent dans l'étape 4. La rotation des groupes de vacances — et son piège historique

Les MARs sont répartis en trois groupes (A, B, C) qui n'ont pas les mêmes priorités de vacances. Pour que personne ne soit servi en premier tous les ans, l'ordre tourne chaque année — dans le sens « le dernier devient le premier », entre les groupes comme à l'intérieur de chaque groupe : ABC devient CAB, puis BCA, puis revient à ABC. Le rang qui en résulte sert aussi, plus tard, à désigner le MAR le moins prioritaire à solliciter en premier quand il faut demander à quelqu'un de décaler ses vacances.

⚠️ Cette règle est écrite à quatre endroits du code (la page du staff, la page d'administration, et deux fois côté serveur). Jusqu'au 30/07/2026, le serveur tournait dans un sens et les écrans dans l'autre : les deux ne coïncidaient qu'une année sur trois, et une année sur trois le MAR désigné en cas de conflit n'était pas celui affiché au staff — constaté en réel sur l'hiver 2027. Toute modification de la rotation doit être répercutée aux quatre endroits.

B3W2 — Générer les gardes

En 2 minutes

L'assistant le plus verrouillé : il vérifie que la génération est possible et juste avant de la lancer. D'abord une salve de contrôles — chaque MAR a-t-il saisi ? reste-t-il des conflits de vacances ? quelqu'un s'est-il rendu indisponible au point de ne plus pouvoir porter sa part ? certains jours sont-ils trop dégarnis ? Puis la validation des vacances, puis le lancement. La génération prend 30 à 60 secondes et enchaîne trois opérations : générer, publier, et envoyer automatiquement à chaque MAR le récapitulatif de ses gardes — sans confirmation supplémentaire.

Les contrôles d'avant-lancement, dans l'ordre
  1. Récapitulatif des saisies : bloque si un MAR n'a pas saisi ses indisponibilités.
  2. Conflits de vacances : bloque s'il reste des conflits de seuil non arbitrés.
  3. Audit d'équité : pour chaque catégorie de garde (samedis, week-ends, jeudis, fériés), l'assistant calcule la part exacte de chacun et vérifie que personne ne s'est rendu indisponible au point de ne plus pouvoir la porter. Bloque, avec un message qui dit précisément quoi débloquer.
  4. Couverture jour par jour : liste chaque journée à moins de 6 MARs disponibles (rouge en dessous de 4, orange à 4-5), le nombre de libérations à obtenir — et le MAR le moins prioritaire (au rang des vacances) à solliciter en premier. Informe, ne bloque pas.
  5. Couverture par semaine : capacité contre besoin, semaines tendues.
Les verrous du lancement

La génération est refusée dans deux cas : l'année visée est 2026 ou avant (l'année 2026 a été saisie à la main et est sanctuarisée), ou l'onglet des gardes de l'année visée existe déjà. Ce second verrou est capital : régénérer une année écraserait la preuve d'équité figée et tous les échanges déjà négociés entre MARs. Régénérer une année déjà générée fait partie des interdits absolus du projet. Pour forcer en toute connaissance de cause, il faudrait supprimer l'onglet à la main dans le classeur — geste volontairement inconfortable.

Repères techniques

Assistant : openWizardGardes. Contrôles chargés en parallèle : getAllIndispos, getConflitsAll, getJoursFeries, getVacValidation (porte les rangs de priorité). Lancement : launchWizardGardes → action generateGardes, qui enchaîne generateGardes → publishPlanning → envoyerRecapIndispos (c'est bien ce nom-là ; « envoyerRecapGardes » n'existe que comme libellé de journal). L'assistant affiche le compte des envois, des MARs sans email et des échecs.

B4W3 — Clôturer l'année

En 2 minutes

Deux étapes : vérifier que l'année suivante est prête, puis archiver — ce qui enchaîne l'archivage proprement dit, la bascule de l'année active, et la fermeture de la campagne de saisie. À savoir absolument : l'archivage retire l'année du classeur maître. Les quatre onglets de l'année (gardes, indisponibilités, affectations, statistiques) sont copiés dans un classeur d'archive puis supprimés du maître. Rien n'est perdu — tout reste consultable dans l'archive — mais l'année quitte le classeur principal.

Ce que fait l'archivage, dans l'ordre
  1. Il reporte le bilan de l'année dans l'onglet HISTORIQUE (sans doublon si l'année y figure déjà). Le décompte Noël/Nouvel An est relu dans les gardes réelles — échanges et dons inclus — pas dans le bilan figé à la génération.
  2. Il range les fichiers nominatifs (statistiques, indisponibilités) dans le Drive privé — jamais dans le dépôt public.
  3. Il copie puis supprime du classeur maître les quatre onglets de l'année, transférés vers le classeur d'archive.
  4. Il purge les retouches manuelles de l'année (et des années antérieures — auto-nettoyant si une clôture avait été manquée).

Deux protections apprises en réel. ① Si la réponse d'un archivage se perd en route et qu'on relance, l'assistant reconnaît qu'il est déjà passé (triple indice concordant) et répond « déjà fait » au lieu d'un faux échec définitif. ② Jusqu'au 30/07/2026, un archivage à moitié réussi (transfert échoué) pouvait passer pour un succès : l'année basculait alors que les onglets étaient encore dans le maître, et il devenait impossible de re-clôturer depuis l'assistant. B5Comment l'algorithme répartit les gardes

En 2 minutes

Sept phases. ① Calculer la cible de chacun — sa juste part, proportionnelle à son temps de travail, dans chaque catégorie (total, samedis, jeudis, week-ends, veilles de férié, fériés), corrigée par le report de l'année précédente. Depuis septembre 2026 cette cible est un nombre entier : 5 ou 6 samedis, jamais 5,4 — une part à virgule n'est atteignable par personne, et l'écart affiché mélangeait alors l'injustice réelle et l'impossibilité arithmétique. ② Placer d'abord les souhaits garantis. ③ Avancer jour après jour en choisissant à chaque fois le meilleur candidat : jamais deux jours de suite, jamais deux week-ends de garde d'affilée, jamais sur une absence, bon espacement, et priorité à celui qui est le plus loin de sa juste part. ④ Rééquilibrer par petits échanges, sans jamais casser une règle dure ni toucher un souhait honoré. ⑤ Poser les récupérations de samedi. ⑥ Écrire le résultat et le bilan d'équité. ⑦ Et par-dessus tout cela : recommencer le calcul jusqu'à huit fois avec des numéros de tirage différents, et n'écrire que le meilleur résultat.

Les chiffres de référence — le contrat de non-régression

La couverture a été éprouvée sur 400 années simulées (20 tirages différents des années 2027 à 2046), soit 292 312 gardes : aucune journée sans binôme de garde.

L'équité a été remesurée après le changement de septembre 2026 — cibles entières, nouvel objectif de l'optimiseur, week-ends interdits — sur 45 années (neuf scénarios d'absences de cinq ans chacun) : 44 années sur 45 où personne ne dépasse une garde d'écart, sur aucun des six axes, contre 29 sur 45 avec la version précédente. La seule exception atteint deux gardes.

Et sur des données réelles. Le 5 septembre 2026, l'algorithme a tourné dans Apps Script sur les absences réelles du service — complétées pour que chacun ait posé tous ses jours, avec 161 souhaits — dans une copie du classeur. Les 364 journées ont toutes été pourvues, y compris le 27 décembre et les 17-18 avril où il ne restait que trois médecins disponibles sur vingt. Un seul MAR à deux gardes d'écart ; 121 souhaits honorés sur 161.

Ces chiffres sont le contrat : si une modification du générateur les dégrade, c'est un signal d'alerte, quelle que soit sa justification.

⚠️ Le piège du zéro. Dans la colonne du pourcentage de gardes, un « 0 » est interprété comme… 100 (une case vide et un zéro se ressemblent pour le code). Pour exempter un MAR de gardes, il existe une case prévue (« NO_GARDE ») — jamais un zéro.

Le bilan est une photo prise à la génération. Il ne bouge plus ensuite, même si des MARs échangent des gardes en cours d'année. Le report vers l'année suivante s'appuie sur cette photo : une petite dérive du calcul commencera à la génération 2028 — connu, accepté pour l'instant, à traiter un jour.

Repères techniques

generateGardes(year) dans generateur_gardes.gs, sous l'interrupteur NOUVEL_ALGO_GLOBAL — à false, le générateur redevient exactement celui d'avant septembre 2026 : c'est le retour arrière, en une ligne.

Cibles entières. La part exacte (5,4 samedis) est diminuée du report de dette, puis arrondie par la méthode des plus forts restes : chacun reçoit sa partie entière, les unités restantes vont à ceux qui sont le plus créditeurs. La somme reste exactement le nombre de gardes à poser — arrondir chaque cible dans son coin promettait 6 jeudis de trop et laissait 6 fériés sans propriétaire (mesuré). Le report étant plié dans la cible, le compteur dette est remis à zéro pour que ratio() ne l'applique pas deux fois. Dette : amortie à 60 %, plafonnée à ±2, lue sur l'année précédente seulement — la version cumulative reste à écrire.

Numéro de tirage. À égalité parfaite, l'ordre de l'onglet MEDECINS ne départage plus : il déplaçait près d'une garde sur trois. L'ordre vient d'un hachage(nom, tirage) ; rejouer le même tirage redonne le même planning, et l'onglet n'est jamais modifié.

Multi-départ. Jusqu'à MULTI_DEPART_MAX (8) calculs à blanc, on écrit le meilleur ; règle d'arrêt à une garde d'écart. Critère de choix, dans l'ordre : journées sans binôme, axes au-delà de 2, pire écart. En pratique un seul tirage suffit dans 25 années sur 45.

Souhaits : placeSouhait, profil « souhait_plafond », jours de semaine seulement — ni week-end ni férié, et jamais au-delà de sa cible totale. Sélection quotidienne : scoreSelect — règles dures (blocked : pas deux jours consécutifs, pas jeudi→samedi, pas de vendredi+dimanche du même week-end hors souhait, et jamais deux week-ends de garde d'affilée — posé à la construction, relâché en dernier recours seulement), puis pénalités d'espacement, puis équité de la catégorie. Le week-end est traité comme une unité vendredi+dimanche.

Rééquilibrage (§8c) : objectif lexicographique. L'optimiseur minimisait une somme de carrés — l'écart moyen — et laissait donc volontiers une personne loin de sa cible si le total y gagnait. Il supprime désormais d'abord tout écart de 2 ou plus (poids LEX_POIDS = 600), et affine la moyenne ensuite. Le poids reste SOUS les 1000 de la règle des week-ends : à 3000, l'équité l'écrasait — 48 enchaînements par an au lieu de 2. canHold interdit de créer un vendredi+dimanche, ou un second week-end consécutif, par transfert.

Une récupération par samedi de garde, hors vacances scolaires. Écriture : GARDES_(année) + STATS_GARDES_(année). Essai à blanc : comparerAlgorithmes(year) — deux calculs sans écriture, ancien et nouvel algorithme, six écarts côte à côte. Garantie de périmètre : le générateur ne contient aucune référence à un secteur — l'équité est intouchable par le chantier du déménagement (§D5). Banc dédié : simulateur/ et banc/banc_nouvel_algo.js.

L'essai à blanc : le seul écran avant de générer (08/09/2026)

C2Le « + » de case à pourvoir

En 2 minutes

Le signal le plus regardé de la grille — et longtemps le moins documenté. Un « + » orange dans une case de bloc ne veut pas dire « il manque quelqu'un » : il veut dire « un habitué de ce secteur manque à l'appel aujourd'hui, et personne ne l'a remplacé ». Les consultations, elles, suivent une règle plus simple, pilotée par les données. Jamais de « + » le week-end ni les jours fériés.

La règle générale, et les quatre exceptions

Qui devrait être là ? Les MARs affectés à ce secteur pour le mois — les « réguliers ». Combien en manque-t-il ? Les réguliers absents ce jour-là, plus ceux que le comité a déplacés ailleurs, moins les personnes présentes dans la case qui ne sont pas des réguliers — elles comptent comme remplaçants. Le résultat donne le nombre de « + ». Une case entièrement vide affiche toujours au moins un « + ».

SecteurSa règle propre
CIRègle générale, sauf le jeudi — ce jour-là, c'est la radio interventionnelle seule.
RIRequis mercredi et jeudi matin uniquement. Jamais l'après-midi, jamais les autres jours, même vide.
MATToujours pourvue, matin et après-midi.
DVIRequis le mardi matin uniquement (pose de DVI).

Pour une consultation, le « + » vaut simplement l'effectif requis moins les présents — le requis étant lu dans le tableau des consultations du classeur (une colonne par demi-journée). Aucun nom de consultation n'est écrit dans le code.

La fragilité à connaître : les secteurs de bloc, eux, sont encore décrits dans le code de la page d'administration, avec leurs noms actuels. Au déménagement, quand les noms de secteurs changeront, le « + » cassera sans message si rien n'est fait — c'est répertorié au §D5.

C3Créer ou retirer un secteur, une consultation

En 2 minutes

Tout se règle dans deux onglets du classeur — SECTEURS pour les secteurs, CS_TEMPLATE pour les consultations — sans toucher au code. Le changement est visible après un rechargement complet de la page (Ctrl+Maj+R). Pour retirer : on passe la colonne ACTIF à « N », on ne supprime jamais la ligne. Réservé à l'administrateur — le comité n'a pas accès au classeur.

Ajouter un secteur — les colonnes qui comptent
ColonneRôle

ORDRELa position d'affichage, partout : légende, planning, fichier Excel.

⚠️ Passer un secteur à « N » le retire de tout l'affichage — y compris des semaines passées déjà publiées. Le mécanisme n'a pas de mémoire. À manier en connaissance de cause, et jamais avant d'avoir réaffecté les MARs concernés.

Ajouter une consultation, avec un exemple complet

Dans le tableau des consultations : une ligne par type, une colonne par demi-journée de la semaine — la semaine se lit d'un coup d'œil. Le nombre inscrit dans chaque colonne est le nombre de créneaux à pourvoir cette demi-journée (0 = aucun). La position de la ligne fixe l'ordre d'affichage.

Exemple — ouvrir une consultation vasculaire le mardi après-midi : une nouvelle ligne « CS-VASC / CS Vasculaire », la colonne du mardi après-midi à 1, tout le reste à 0, un libellé et une couleur pour l'Excel. Après rechargement : une case « à pourvoir » apparaît chaque mardi après-midi, le comité clique dessus pour placer quelqu'un, et une ligne VASCULAIRE sort dans l'Excel du vendredi.

Ne pas oublier le lien retour : renseigner la colonne CS du secteur concerné dans l'onglet SECTEURS. Sans ce lien, le panneau proposera les MARs dans l'ordre habituel au lieu de mettre en tête ceux du secteur.

Détail d'étiquettes : les mentions « / URO. » et « / OPHTALMO. » du fichier Excel sont des raccourcis de langage — le bloc viscéral couvre viscéral et uro, le bloc ORL couvre ORL et ophtalmo. Il n'existe pas d'identifiant distinct pour ces spécialités.

Retirer proprement

Supprimer une ligne ne supprime pas les affectations qui pointent vers elle : elles gardent l'ancien identifiant, que le système ne reconnaît plus — à la publication suivante, les MARs concernés basculent en « volant », et l'identifiant disparaît du sélecteur (impossible de le rechoisir). Rien n'est perdu, mais c'est le désordre. Marche à suivre : réaffecter d'abord les MARs concernés, republier, puis passer ACTIF à « N ». C'est exactement le mécanisme prévu pour le déménagement : anciens secteurs à « N », nouveaux ajoutés, aucune ligne effacée. Le diagnostic signale toute affectation qui pointe vers un secteur inexistant, inactif ou non affectable, en nommant les MARs concernés.

C4Consultations à venir & accès du secrétariat

En 2 minutes

La page « Consultations à venir » répond à une question : le médecin qui voit ce patient en consultation sera-t-il présent le jour de l'intervention ? Une seule page, deux portes : un MAR (code personnel) y voit ses propres consultations, motifs d'absence affichés ; le secrétariat (code partagé) les voit toutes, mais les motifs ne lui sont jamais envoyés — le tri est fait par le serveur, pas par la page. Lecture seule, aucune donnée de patient.

Pourquoi le secrétariat ne peut vraiment rien voir d'autre

Le rôle secrétariat fonctionne en « tout est interdit, sauf deux actions » : se connecter, et obtenir la liste des absences pour la fenêtre demandée. La liste des actions autorisées tient en un seul endroit du code — pas de garde ajoutée au cas par cas, qui finirait par en oublier une.

Le masquage des motifs est fait par le serveur : en session secrétariat, le motif n'est tout simplement pas joint à la réponse. Le masquer dans la page aurait laissé l'information lisible dans les coulisses du navigateur.

Ne jamais élargir cette liste au planning publié. Un audit (26/07) a montré que le fichier du planning contient le code d'absence brut de chaque MAR pour l'année entière : y donner accès au secrétariat viderait de son sens la règle « les dates, jamais les motifs ». Au relais Cloudflare, le secrétariat ne lit d'ailleurs rien du tout.

Ce qui compte comme « absent » — et les trois cas ajoutés à la main

Les absences viennent du planning publié (si ce n'est pas publié, ça n'existe pour personne). Être de garde ne compte volontairement pas comme absent : un MAR de garde peut assurer une intervention libérale. Trois situations ne figurent dans aucun planning et sont ajoutées par le serveur : le jour fixe non travaillé d'un temps partiel, la semaine « off » d'un rythme en alternance, et la période hors contrat (avant l'arrivée ou après le départ d'un MAR). Un MAR hors contrat sur toute la fenêtre est retiré de la réponse entière — sinon il apparaîtrait « présent tous les jours » et serait proposé comme remplaçant : précisément le faux « disponible » que l'outil doit empêcher.

Le piège des consultations de maternité : elles n'existent dans aucune donnée. La règle est « mardi et jeudi matin, la personne en maternité tient aussi la consultation », et elle est recalculée à l'affichage — la case du planning dit MAT, jamais CS-MAT. Chercher les consultations par leur préfixe les rate toutes. Cette règle vit à deux endroits (l'affichage de la page d'administration, et le serveur pour cette page-ci) : si la maternité change de jours, il y a deux endroits à modifier.

Repères techniques

Page : absences.html. Liste blanche : SECRETARIAT_ACTIONS (en tête d'Indispos.gs) = login + getConsultAbsences. Codes considérés absents : ABSENT_CODES (code.gs) = RG V F CTP CP R A TP CL ; ajouts serveur : TP (jour fixe), OFF (semaine off), HS (hors contrat). Règle maternité côté page : MIROIR_MATER + estMiroirMater() (admin.html) ; côté serveur : dans getConsultAbsences. Mise en service : la tuile « Mes consultations » du portail est encore restreinte (réglage only) le temps que le comité pose les consultations à 4 semaines ; pour l'ouvrir — retirer la restriction, monter la version du site, compléter le guide MAR.

C5La boîte de réception (Messages)

En 2 minutes

Le bouton ✉ Messages de la page d'administration affiche les mails reçus sur l'adresse du projet — celle à laquelle les MARs écrivent leurs demandes. Réservé au comité. Une pastille indique le nombre de non-lus (alimentée par le relais, mise à jour localement à chaque lecture) ; le contenu d'un message n'est chargé qu'au clic ; l'ouvrir le marque « lu ». Répondre depuis la page n'est pas prévu — volontairement.

Les choix de sécurité et de sobriété
  • L'autorisation demandée à Google est la plus étroite possible qui permette de marquer un message « lu » (sans quoi le compteur ne bougerait jamais). Elle ne permet pas la suppression définitive. Toutes les autorisations du projet sont consignées dans le dépôt.
  • Contre les mails piégés, deux barrières : le serveur ne renvoie que du texte pur (la mise en forme d'un mail est convertie côté serveur et ne part jamais), et la page affiche ce texte sans jamais l'interpréter comme du code.
  • Sobriété : le compteur ne ralentit pas l'ouverture de la page (il vient du relais), et le corps des messages n'est chargé qu'à la demande.

Bon à savoir : Google ne retire jamais une autorisation déjà accordée. Restreindre la liste dans le dépôt ne suffit pas — il faut révoquer explicitement l'accès dans les réglages du compte, relancer une fonction pour redemander le consentement, puis redéployer. Le site est hors service entre la révocation et le redéploiement.

Repères techniques

Trois actions serveur, admin seul : mailNonLus, mailListe (20 messages), mailMessage. Service avancé Gmail (pas GmailApp), autorisation gmail.modify, manifeste versionné dans gas/appsscript.json. Compteur : copie mail_nonlus du relais, décrément local à la lecture (comportements couverts par le banc). Piège d'encodage résolu : Gmail encode les corps en base64 « URL-safe » sans remplissage, que l'outil standard de décodage refuse (~2 messages sur 3) — normalisation manuelle avant décodage. Quota : 20 000 opérations Gmail/jour, usage réel ~12 % en charge.

C6Les mails automatiques de changement de planning

En 2 minutes

Le principe : on ne surveille pas les gestes du comité, on compare deux photos du planning — l'état actuel et l'état au dernier envoi. Un changement posé puis annulé avant l'envoi ne produit donc aucun mail. Chaque publication (re)démarre un compte à rebours de 10 minutes : les mails ne partent qu'après une accalmie complète, jamais au milieu d'une salve de retouches. Si le module tombe en panne, la publication n'en souffre pas.

Les réglages, et l'état actuel

Trois interrupteurs (dans les réglages du serveur, modifiables sans redéploiement) : l'allumage général du système ; une adresse de test qui, si elle est renseignée, détourne tous les mails vers elle (personne d'autre n'en reçoit) ; et l'année surveillée, posée automatiquement. Dans le classeur, une colonne de l'onglet MEDECINS permet de désabonner un MAR ; colonne absente = tout le monde est notifié.

État actuel : EN TEST jusqu'après la démonstration du 4 septembre. L'adresse de test est renseignée avec celle de l'administrateur : tous les mails y sont détournés, aucun MAR n'en reçoit. Pour ouvrir le service : vider l'adresse de test, vérifier l'allumage, nettoyer l'année surveillée après les essais sur 2027, et retirer les encadrés « pas encore en service » des guides comité et MAR.

Quatre garde-fous à connaître avant de conclure à une panne
  1. La toute première exécution ne fait qu'une photo — il n'y a rien à comparer. Il faut deux publications espacées pour voir le premier mail. Ne pas conclure à une panne au premier essai.
  2. La photo de référence n'avance que si tous les envois ont réussi : un changement non annoncé sera repris à la publication suivante plutôt que perdu.
  3. Après une génération annuelle, remettre la photo à jour sans envoyer (fonction prévue) — sinon des milliers de journées « changées » partiraient d'un coup. Le récapitulatif de W2 joue déjà ce rôle auprès des MARs.
  4. Après un test sur une autre année, penser au ménage : supprimer la photo de test du Drive, vider l'année surveillée et l'adresse de test.

Ce que la redirection d'essai détourne — et ce qu'elle ne détourne pas. NOTIF_EMAIL_TEST ne concerne que ce module, les mails de changement de planning. C7La veille bibliographique

En 2 minutes

Chaque lundi à 6 h, le serveur interroge PubMed, la grande base des publications médicales, et alimente la tuile Veille du portail. La règle de sélection : un article n'entre que s'il vient d'une revue de la liste (23 revues d'anesthésie-réanimation, plus 18 grandes revues généralistes) et qu'il correspond à l'un des 21 thèmes du métier. Résultat : environ 73 articles par semaine, chacun étiqueté avec ses thèmes. Chaque MAR a ses propres marques « lu » et « ★ » — ce qu'un collègue lit reste personnel.

Pourquoi ces règles précises — l'histoire courte

Chaque règle vient d'une mesure faite sur PubMed (les 3 et 8 août 2026), pas d'une intuition — et les mesures sont conservées en tête du fichier pour qu'on ne refasse pas le chemin à l'envers :

  • « Revue ET thème », pas « revue OU thème » : l'ancienne règle interrogeait tout PubMed sur les thèmes et produisait 95 % du volume… et tout le bruit (des revues de génétique, de sommeil, de néphrologie).
  • Le filtre « études humaines » a été assoupli : l'étiquette officielle « humains » n'est posée par PubMed que des semaines après la parution — elle rejetait donc tous les articles récents. Désormais on n'écarte que les études animales avérées.
  • Les grandes revues généralistes sont filtrées par type d'étude (essais randomisés, méta-analyses, recommandations…) : sans cela, elles déversaient un millier d'articles dès qu'un mot d'un thème apparaissait. Les revues de la spécialité, elles, entrent sans ce filtre — il les appauvrissait sans réduire le bruit.
  • Les demandes sont paginées et envoyées dans le bon format : l'ancienne version tronquait silencieusement la liste des revues (trop longue pour le format utilisé) et, en cas de trop-plein, gardait précisément les articles les moins bien indexés.
  • Les thèmes sont cherchés dans le titre et le résumé, disponibles dès la parution — jamais dans les étiquettes officielles, qui arrivent avec des semaines de retard.

Ce que le module ne fait pas : classer les articles par qualité. Le tri fin est un chantier distinct — il a été mesuré que resserrer encore le vocabulaire coûte plus de couverture qu'il ne réduit de volume. La liste des revues et des thèmes se modifie dans l'onglet VEILLE_CFG du classeur (mode d'emploi : docs/VEILLE_CFG-mode-emploi.md).

Les marques « lu » et « ★ » : personnelles, et jamais perdues

Depuis la v1.30, les marques sont propres à chaque MAR (avant, une seule case servait pour tout le service). Trois précautions les rendent fiables :

  • L'identité vient de la connexion, jamais de ce que la page prétend : impossible de marquer à la place d'un collègue.
  • L'écran est mis à jour immédiatement, et l'envoi part en arrière-plan ; s'il échoue (réseau coupé), la marque est gardée dans une petite file locale du navigateur et renvoyée plus tard. Renvoyer deux fois la même marque est sans danger.
  • Au relais Cloudflare, chacun ne reçoit que ses propres marques — l'admin compris : ce qu'un collègue lit est personnel. Sur un autre appareil, la marque apparaît en une à deux minutes.

C11Mesurer la vitesse des pages

En 2 minutes

Deux commandes à taper dans la console du navigateur (touche F12) : chrono() imprime le budget complet de l'ouverture d'une page — qui a pris combien de temps, et où ; chronoClics() fait pareil pour chaque clic. Elles ne modifient rien, elles observent. La grande leçon de toutes les mesures : le levier le plus rentable n'est pas d'accélérer le travail du serveur, c'est de réduire le nombre de demandes — chaque demande au serveur Google paie ~3 secondes de péage fixe avant de commencer à travailler.

Les trois leçons durables des mesures
  1. Une seule demande à la fois. Le serveur Google met en file les demandes de tous les utilisateurs : en envoyer plusieurs en parallèle ne fait rien gagner, cela transforme une attente ordonnée en bousculade. Mesuré : la même demande a coûté 8,5 secondes lancée en parallèle, 1,8 seconde partie seule. Les pages appliquent ce principe (file d'attente interne) — ne jamais revenir aux demandes parallèles « pour aller plus vite » : l'erreur a été commise une fois, elle coûtait 15 secondes à chaque ouverture.
  2. Se méfier des coupables évidents. Trois suspects « évidents à la lecture du code » ont été mesurés… et innocentés : le réaffichage complet de la semaine coûte 17 millièmes de seconde ; le poids de la page d'administration coûte 2 % de son ouverture ; le décodage d'une grosse réponse coûte 6 millièmes. Le vrai coût d'un clic, c'est le dessin à l'écran. Mesurer d'abord, conclure ensuite.
  3. Ne jamais comparer deux mesures prises à des heures différentes. Google n'offre aucune garantie de régularité : le même code est passé de 3 à 6 secondes en trois heures, sans changement. Un avant/après n'a de sens que dans la même session, à quelques minutes d'intervalle.

Un coût connu à garder en tête : servir un document PDF (topos, protocoles) est l'action la plus chère du portail (6 à 11 secondes) — à éviter collectivement en pleine réunion.

Repères techniques

Disponibles sur les pages d'administration, de planning, du portail, des indisponibilités et des consultations. chrono() ventile chaque demande en trois temps : « avant » (notre code préparatoire — quelques millièmes grâce à la mémoire tampon de configuration), « travail » (le temps utile, détaillé opération par opération), « réseau » (le péage : ~1,5 s de recompilation Google + ~1,65 s de transport et de file). Les lignes miroir: mesurent les lectures du relais (0,15 à 1 s selon le colis) et donnent la cause d'un éventuel repli. chronoClics() donne, par clic : attente, traitement, dessin (repères : au-delà de 0,2 s un clic paraît lent, de 0,5 s bloqué) — Chrome et Edge seulement, la mesure n'existe pas sur Safari/Firefox.

C12Les échanges de gardes & les notifications

En 2 minutes

Les MARs se donnent ou s'échangent des gardes directement, sans le comité : l'un propose depuis son portail, l'autre reçoit une notification sur son téléphone, accepte ou refuse. S'il accepte, le planning s'écrit par le chemin d'écriture historique (applyModification), avec tous ses garde-fous — rien de nouveau ne touche à la grille. Chaque demande vit dans l'onglet ECHANGES du classeur, avec son état : en attente, acceptée, refusée, expirée, ou impossible (le planning a bougé entre la proposition et l'acceptation — rien n'est écrit, les deux sont prévenus). Sans réponse : rappel unique à 24 h, expiration à 48 h.

Ouvrir, fermer : l'interrupteur

Qui a accès aux échanges (et à la carte d'activation des notifications) se commande depuis l'éditeur Apps Script, sans rien redéployer — effet dans la minute :

  • Ouvrir à tout le service : exécuter ouvrirEchanges() (fichier echanges). Refermer : fermerEchanges().
  • Avant l'ouverture, seuls le comité et les éventuels pilotes d'essai voient quelque chose. Les pilotes se déclarent dans la propriété de script ECHANGES_PILOTES (identifiants séparés par des virgules — ils restent dans les propriétés, jamais dans le dépôt). Après toute retouche de cette propriété : exécuter synchroniserEtatEchanges().

Le verrou est tenu côté serveur : tant que l'interrupteur est fermé, le relais refuse de servir les demandes d'échange et refuse les abonnements aux notifications — les pages n'ont donc rien à cacher, elles ne reçoivent simplement rien. Personne ne peut « deviner l'adresse ».

Notifications de changement : une file d'années, un abonnement par personne

Qui reçoit quoi. Les écarts sont regroupés par MAR (_notifDiff) : chacun reçoit un seul mail, avec ses propres changements et rien d'autre.

Le filtre statut / secteur. Un changement de statut (garde, astreinte, absence) est toujours signalé, quelle que soit la date — un déplacement de garde en mars part immédiatement. Un changement de secteur (l'affectation en journée) n'est signalé que s'il tombe dans la fenêtre du dernier Excel diffusé : au-delà, l'Excel du vendredi suivant fera foi de toute façon, un mail n'apporterait rien.

La fenêtre (_notifSemaineExcel) court du dernier vendredi 16 h déjà passé jusqu'au dimanche neuf jours plus tard. Elle englobe volontairement le samedi et le dimanche qui appartiennent encore à l'Excel précédent : élargissement pur, aucune date n'est retirée entre deux diffusions.

L'interrupteur de sécurité. Quand NOTIF_ACTIVE ne vaut pas O, _notifEnvoyerAnnee_ prend quand même la photo et se tait (journal : « système éteint, photo prise, aucun envoi »). Conséquence pratique : aucun arriéré ne peut s'accumuler tant que le système est éteint — c'est le moyen sûr de traverser une période de tests ou une démonstration, bien plus que de manipuler les fichiers _notifie.json. NOTIF_EMAIL_TEST est un second filet, indépendant : il détourne les mails de changement vers une seule adresse, sans effet sur le récapitulatif annuel « Vos gardes », qui lit toujours la colonne EMAIL du classeur.

(25/08/2026) File d'années. notifPlanifier écrasait la propriété NOTIF_YEAR à chaque appel : publier 2027 faisait oublier les changements de 2026 encore en attente. La photo de référence (planning_{Y}_notifie.json) n'étant recalée qu'après un envoi réussi, ils s'accumulaient et repartaient tous d'un coup à la publication suivante de cette année-là. Trace du 23/08 : 27 fiches appliquées sur 2026 entre 14h31 et 14h38, génération 2027 à 14h48 (l'année est écrasée), minuteur à 14h59 qui ne regarde que 2027 — les 27 modifications ont attendu jusqu'au 25/08 23h29, où elles sont parties en une rafale de 25 changements et 13 mails. La propriété porte désormais une file d'années, toutes traitées ; l'ancien format (année seule) reste lu ; une année dont l'envoi échoue y retourne.

Un abonnement par personne, pas par appareil. Le relais range l'abonnement push sous notif_sub_<id> : s'abonner depuis un second appareil écrase le premier. Se connecter avec le compte d'un collègue pour une démonstration lui coupe donc ses notifications, et la carte d'activation étant masquée une fois abonné, il n'a pas de bouton évident pour les rétablir — il lui faut réinitialiser la permission dans les réglages du téléphone, ou réinstaller le raccourci.

Quota. Le contrôle est fait avant tout envoi (_quotaEmailInsuffisant_) : en cas d'insuffisance rien ne part, le journal porte « Envoi REFUSÉ », et la photo n'est pas recalée — les changements ne sont pas perdus mais ne repartiront qu'à la publication suivante. Aucune reprise automatique le lendemain à ce jour.

Les contrôles : joués deux fois, écrits une

À la création d'une demande, toutes les règles du service sont vérifiées immédiatement — mêmes juges que l'écriture réelle, mais sans rien écrire : un refus (collègue en congé, repos qui tomberait sur une absence…) s'affiche sur-le-champ, jamais 48 h plus tard. À l'acceptation, tout est rejoué pour de vrai, car le planning a pu bouger entre-temps. Aucune règle n'est écrite deux fois dans le code : c'est le même juge qui tranche aux deux moments.

Le samedi et sa récupération

Depuis la génération de novembre 2026, le générateur note dans l'onglet LIENS_R_{année} quel jour de récupération correspond à quel samedi (une ligne par samedi et par tenant — un samedi a deux gardes, donc deux lignes). Quand un samedi change de mains, la récupération de ce samedi est transférée au receveur, à sa date, et la ligne suit. Trois cas d'échec prévus — année sans lien (2026), récupération déjà prise, receveur occupé ce jour-là — laissent l'échange valide et déclenchent une notification au comité : « Récupération à replacer ». Un échange samedi contre samedi ne déplace aucune récupération (le compte de chacun ne change pas). L'onglet suit le même cycle annuel que GARDES et STATS (archivé avec eux).

Les notifications : ciblées, avec une pastille unifiée

Les notifications d'échange ne partent qu'à la personne concernée — jamais de bruit pour les autres. Depuis le 23 août 2026, la pastille rouge de l'icône de l'app obéit à une seule logique, tous motifs confondus : c'est un compteur de non-vus, tenu par le relais (une clé notif_cpt_<id> par MAR, +1 à chaque envoi), remis à zéro quand le MAR ouvre son dashboard (route /notif-vu, et le chiffre local s'efface aussitôt). Le nombre de demandes en attente que les échanges calculaient de leur côté est désormais ignoré par le relais — deux chiffres qui se disputent l'icône, c'est un chiffre faux ; son calcul, devenu inerte, sera retiré au prochain lot echanges.gs. Deux garanties de conception inchangées : une pastille qui échoue n'empêche jamais la bannière de s'afficher, et une notification qui échoue n'empêche jamais le geste d'aboutir. Les abonnements de téléphones disparus se purgent tout seuls au premier envoi qui les trouve morts.

La cloche : le serveur note ce qu'il envoie

Une notification est périssable — téléphone éteint, refusée, lue et oubliée. Depuis le 23 août 2026, le serveur tient donc un registre de ce qu'il envoie : au moment de chaque envoi, et avant même de le tenter, notifierPush_ (miroir.gs) inscrit une ligne dans l'onglet NOTIFS_JOURNAL (QUAND | MAR | TITRE | CORPS | URL) — la ligne existe même si le push rate. Le dashboard l'affiche sous une cloche : les 30 derniers jours, groupés par date, chaque ligne menant à sa page. Le destinataire est un identifiant, ou * pour « tout le monde » — la génération s'y enregistre ainsi, puisqu'elle s'adresse à tous les MARs. Une cible visant le comité n'y entre pas (il n'a pas de cloche), le test du canal non plus. Défaut corrigé le 6 septembre 2026 : le garde-fou écartait en réalité tous les rôles, y compris celui des MARs — donc la notification de génération, la plus importante de l'année. Le push partait sur les téléphones, la cloche restait vide, et rien ne pouvait le révéler puisque la notification, elle, arrivait bien. La rétention se purge au fil de l'eau, à chaque écriture — aucun déclencheur dédié.

Le transport suit le chemin le plus court : une clé notifs de la copie rapide, que le relais sert filtrée à l'identité — chacun ne reçoit que ses entrées et celles adressées à tous, quel que soit son rôle, comme les marques de veille. Elle voyage dans l'appel d'ouverture existant du dashboard : zéro requête ajoutée, zéro milliseconde. Les compteurs notif_cpt_*, eux, sont scellés : ni lisibles par /read, ni poussables par /push. Un futur motif de notification — les changements de planning, aujourd'hui par mail — rejoindra la cloche par un appel de plus à _notifJournalNoter_, sans refonte.

Quatre pièges connus

1) Une icône demandée par une page mais absente du petit fichier d'icônes local s'affiche en carré vide, sans erreur — le banc le vérifie désormais pour toutes les pages. 2) La liste des échanges voyage dans l'appel d'ouverture du portail, avec le planning : ne jamais lui créer un appel séparé — et la règle vaut pour la clé notifs de la cloche, transportée par le même appel. 3) La lecture de l'onglet ECHANGES ne le crée jamais (la synchronisation horaire passe par là) — seule la création d'une demande le fait. 4) Avant la première synchronisation complète qui suit un déploiement, la clé notifs n'existe pas : la cloche reste simplement cachée, sans erreur ni repli — c'est voulu.

C13La pose des temps partiels après génération

En 2 minutes

Depuis le 23 août 2026, le circuit est inversé : les gardes se génèrent d'abord, les jours de temps partiel se posent ensuite, dans ce qui reste. C'est ce qui garantit, par construction, qu'un repos de garde ne tombe plus jamais sur un jour non travaillé — sans une ligne de contrainte supplémentaire dans le générateur. Le MAR concerné voit une carte dédiée sur son portail, choisit ses jours sur un calendrier en trois couleurs, et le comité tranche depuis l'onglet Équipe. Un jour accordé s'écrit en TP dans GARDES_{année} — l'onglet maître du planning — et nulle part ailleurs.

Côté MAR : six états, un plafond

Le calendrier (page des indisponibilités, en mode temps partiel) montre chaque jour ouvré en vert (libre : la pose est directe), jaune (tendu : un jour du service encore ouvert, mais serré — le comité tranchera), violet plein (posé et acquis), violet pâle en pointillés avec une horloge (demandé, en attente du comité), noir (fermé — jour de garde, jour déjà pris, ou jour fermé par un refus du comité) ou gris (impossible : repos, récupération, congés, week-end, férié). Une garde de 18 h ferme le jour : on est au travail.

Le jaune appartient au service, le violet vous appartient : les deux portaient la même couleur avant le 6 septembre 2026, on ne savait donc pas si un jour était encore libre ou déjà demandé par soi.

L'écran sert toute l'année, pas le temps d'une campagne : un jour de temps partiel déjà écoulé garde sa couleur, en atténué — il est figé mais reste compté dans le quota. Il se confondait avec les jours impossibles, alors qu'il ne dit pas du tout la même chose. La jauge se lit en trois temps : déjà pris, posé à venir, en attente du comité. Les marques « indisponible » ou « garde souhaitée » de la campagne, elles, ne ferment rien — elles n'avaient de sens qu'avant la génération. Le quota de jours découle de la quotité du MAR, et le plafond est commun : accordés + en attente ≤ quota. À l'enregistrement, un récapitulatif, puis une notification à chaque décision du comité (validé, refusé, remis en attente).

Côté comité : des décisions en lot

Les demandes en attente s'affichent dans l'onglet Équipe de la page d'administration, avec le nombre de présents recalculé à chaque décision. Le comité marque valider ou refuser, librement et réversiblement — puis clique « Enregistrer les décisions », et là plus rien ne s'annule : un refus fermé par erreur se rouvre en supprimant sa ligne dans TP_FERMES. Un refus ferme le jour pour toute l'équipe, pas seulement pour le demandeur.

Où vit chaque chose

Accordé → TP dans GARDES_{année}, écrit en case vide seulement, effacé seulement s'il s'agit bien d'un TP, relu juste avant chaque écriture. TP fait partie des codes d'absence : le MAR sort automatiquement de son secteur. En attente → rien dans le planning, une ligne dans TP_DEMANDES (ANNEE | DATE | MAR | QUAND). Refusé → rien à défaire, et le jour se ferme dans TP_FERMES (ANNEE | DATE | PAR | QUAND). Ces deux onglets ne sont rattachés à aucune année : leur purge fait partie du ménage d'après-démo, ligne à ligne sur la colonne ANNEE.

La republication différée

Chaque validation devrait republier le planning (~10 s) ; personne ne doit attendre ça après un clic. La republication est donc différée et mutualisée par un déclencheur : le classeur est juste immédiatement, le planning publié rattrape dans la minute. Le seul symptôme visible : une décision qui « ne s'affiche pas encore » — elle est déjà dans le classeur, qui fait foi.

Un piège connu

La part de garde est due inconditionnellement : aucune pose de temps partiel, par aucun chemin, ne réduit la cible de gardes d'un MAR. Le vieux mécanisme des jours fixes (TP_JOURS_FIXES de MEDECINS) neutralisait à tort une cible d'axe — il est neutralisé et sa suppression est planifiée après septembre 2026.

D1Les trois chemins de mise en ligne & le numéro de version

En 2 minutes

Trois chemins, selon ce qu'on livre. Les pages du site : pousser dans le dépôt suffit — c'est en ligne. Le serveur Google : pousser ne suffit pas ; il faut recopier les fichiers dans l'éditeur de Google, puis déployer une nouvelle version — tant que ce n'est pas fait, l'ancien code tourne. Le relais Cloudflare : recopier le fichier dans son tableau de bord et déployer. Règle d'ordre quand une livraison touche plusieurs chemins : Cloudflare d'abord, le serveur ensuite, les pages en dernier — celui qui consomme toujours après celui qui fournit. Et toute modification d'une page visible s'accompagne, dans le même envoi, de la montée du numéro de version du site.

dépôt → tableau de bord Cloudflare → remplacer le code → Deploy
contrôle : la page d'accueil du relais affiche sa version
▼puis
② Le serveur Google
dépôt → recopie manuelle dans l'éditeur Apps Script → Déployer → nouvelle version → rechargement complet des pages
contrôle : le diagnostic compare les versions en service à celles du dépôt
▼puis
③ Les pages du site
pousser dans le dépôt (un lot = un seul envoi) → en ligne → Ctrl+Maj+R
contrôle : relire la version en ligne après l'envoi
Pourquoi cet ordre : une page mise à jour avant son serveur demanderait des choses que l'ancien serveur ne connaît pas encore.
La règle qui sauve, côté serveur

Pousser dans le dépôt ne met pas le serveur à jour : le dépôt n'est que la référence. Pour que le nouveau code tourne, il faut le recopier dans l'éditeur de Google — les dix fichiers concernés, plus le module partagé — puis publier une nouvelle version de l'application web. Les pages appellent une adresse figée sur une version : sans ce dernier geste, l'ancien code continue de tourner, y compris pour une génération lancée depuis l'assistant. (Seule exception : une fonction lancée à la main depuis l'éditeur exécute le code du moment.)

La règle qui sauve — ne jamais modifier le code directement dans l'éditeur de Google sans l'enregistrer aussitôt dans le dépôt : à la prochaine recopie dépôt → éditeur, la modification non enregistrée serait écrasée sans prévenir.

Le numéro de version du site — la règle exacte

Toute modification d'une page visible s'accompagne, dans le même envoi, de la montée du numéro : petit correctif → troisième chiffre (v1.3.1 → v1.3.2) · nouvelle fonctionnalité → deuxième chiffre · refonte majeure → premier chiffre · une modification du serveur seul → pas de montée.

Le 5 septembre 2026, la numérotation est repartie à v1.0. La série v1.x était montée à 99 non pas parce que le portail avait changé 99 fois de visage, mais parce qu'on montait le 2e chiffre à chaque lot ; passer à v10 n'avait fait que déplacer le problème. v1.0 est la version présentée au staff du 4 septembre, celle que l'équipe utilise ; v2.0 est réservé à l'ouverture du module libéral. Le numéro descend donc une fois — c'est voulu. Conséquence à retenir : un numéro ne peut plus dater une fonctionnalité. Trois contrôles du banc le faisaient (« au moins v1.77 », « a dépassé v1.95 ») ; ils vérifient désormais la présence de la fonctionnalité et la forme du numéro. Le numéro apparaît à plusieurs endroits (une constante dans le code, le badge affiché, la ligne d'en-tête des guides) : la règle opératoire est de chercher dans tout le dépôt les fichiers qui portent un marqueur de version et de les mettre tous à jour — ne se fier à aucune liste écrite, compter. Le diagnostic vérifie ensuite la cohérence sur quatre fichiers (la page d'administration, le portail, et les deux guides utilisateurs), en comparant toutes les formes du numéro présentes dans chacun — une leçon du 20/07 : l'ancien contrôle ne lisait qu'une seule forme et a proclamé « tout aligné » pendant des semaines alors que trois fichiers sur quatre affichaient un numéro périmé.

Pousser proprement : le rituel complet
  1. Repartir de la version en ligne du fichier, jamais d'une copie locale qui a pu vieillir.
  2. Un lot de plusieurs fichiers = un seul envoi groupé — fichier par fichier, le site se republierait à chaque fois, et seule la dernière publication compterait.
  3. Avant : vérifier la syntaxe du code, l'équilibre des balises des pages, et passer le banc d'essai (§D2) — tout au vert, sinon on ne propose rien.
  4. Après : relire la version en ligne et vérifier les numéros de version.
  5. Si GitHub est en panne : on peut encore lire par le chemin de secours, mais on n'écrit jamais sans pouvoir contrôler le résultat.

D2Le banc d'essai

En 2 minutes

Le dossier banc/ du dépôt fait tourner le vrai code du projet — le serveur, le relais, les pages — dans un décor entièrement simulé : un faux Google avec un faux classeur rempli de données réalistes, un faux Cloudflare, et même un faux navigateur où les pages sont pilotées au clic. Au 9 août 2026 : 546 vérifications, toutes au vert. Règle absolue : avant toute proposition de mise en ligne touchant une page principale ou le serveur, le banc tourne, et on ne présente le résultat qu'une fois tout au vert. Chaque nouveauté part avec son test ; chaque défaut trouvé en production devient un scénario du banc.

Ce que le banc prouve — et ce qu'il ne prouve pas

Il couvre le cycle annuel complet, les gestes du comité, le relais, le journal, la veille, les pages des MARs, des scénarios de panne (que se passe-t-il quand Cloudflare tombe en pleine écriture ?), et des « tests de contrat » — par exemple, il lit la vraie page du portail pour vérifier que les filtres qu'elle utilise correspondent bien à ce que le serveur envoie.

Le banc prouve la logique, jamais l'infrastructure. « Le banc est vert » ne veut pas dire « ça marche » : les quotas de Google, les latences réelles, les autorisations, les automatismes installés et l'état du déploiement ne sont pas simulés. Le banc élimine les régressions de logique ; la confirmation en production reste indispensable.

Deux règles d'entretien : toute nouvelle fonction de Google utilisée dans le code du serveur doit recevoir son équivalent simulé dans le banc ; et quand plusieurs conversations de travail avancent en parallèle, relancer le banc sur une photographie fraîche du dépôt juste avant l'envoi. Le générateur de gardes a en plus son banc dédié — 400 années simulées (§B5).

Repères techniques

Lancement : cd banc && ./lancer.sh. Les rouages : stubs.js (les fonctions Google simulées), monde.js et jeu_donnees.js (le faux classeur), interface.js (le pilotage des pages au clic, via jsdom), banc_worker.mjs (le vrai code du relais exécuté tel quel).

D5Points de fragilité connus & le déménagement 2027

En 2 minutes

Ne vivent ici que les points durables — l'avancement des chantiers vit dans la feuille de route (docs/ROADMAP-Planning-Med.md), un état d'avancement recopié à deux endroits finit toujours par mentir. À retenir : quatre règles de secteurs restent volontairement écrites dans le code jusqu'au plan du nouvel hôpital ; deux listes de la page d'administration casseront en silence au changement des noms de secteurs si rien n'est fait avant ; et les colonnes de l'onglet MEDECINS s'ajoutent toujours en fin d'onglet, jamais au milieu.

Les quatre règles de secteurs encore dans le code (gelées volontairement)

L'onglet SECTEURS règle couleurs, libellés, ordre et activité sans toucher au code. Mais ajouter, renommer ou supprimer un identifiant de secteur touche encore quatre règles écrites dans le code : la trame des consultations automatiques (endormie), le lien garde→secteur (le médecin de garde réa est placé en réa, celui de mater en mater — renommer ces secteurs casserait ce placement automatique), les règles liées à un jour précis (le jeudi de la radio interventionnelle, le mardi des DVI), et le dictionnaire des synonymes d'affectations (écrit en double, à dédupliquer).

Décision actée : ces quatre points restent gelés tant que le plan du nouvel hôpital n'est pas connu — les réécrire à l'aveugle serait concevoir dans le brouillard. Ce paragraphe est la carte exacte du jour venu. Garantie : le générateur de gardes ne mentionne aucun secteur — l'équité est hors de portée de ce chantier.

Ce qui cassera en silence au déménagement si rien n'est fait

Dans la page d'administration, deux listes de secteurs sont écrites en dur : celle qui pilote le « + » de case à pourvoir, et celle des effectifs cibles. Au changement des identifiants de secteurs, elles casseront sans aucun message d'erreur. La solution retenue — les piloter depuis l'onglet SECTEURS via une colonne dédiée — n'est pas encore construite. À traiter avant la bascule. La décision préalable qui conditionne tout : la finesse des affectations dans le nouvel hôpital (grands secteurs ou sous-secteurs).

Les pièges durables, vérifiés en réel
  • Colonnes de MEDECINS : toujours en fin d'onglet. De nombreuses lectures repèrent les colonnes par leur position : une colonne insérée au milieu a rendu les codes d'accès inopérants (constaté le 21/07/2026). Le bon modèle — repérer par le titre — est documenté dans le guide du fichier maître.
  • L'échange de gardes de jours adjacents est refusé par le système, qui préfère refuser que risquer une perte silencieuse. La correction (relire avant d'écrire, plus le cas particulier de la récupération du samedi) est prévue après le 4 septembre — avec son scénario de banc obligatoire avant d'y toucher.
  • Deux pièges de lecture du code, pour le mainteneur : le panneau de placement est décrit en pleine largeur dans son attribut de style, mais une règle plus bas dans la feuille de style le transforme en tiroir flottant — lire la feuille de style, pas seulement l'attribut ; et la fonction de formatage de dates renvoie le texte « undefined » (et non du vide) quand on l'appelle sans valeur — les valeurs par défaut ne se déclenchent alors jamais.
  • Un réglage inerte : la ligne ARCHIVE_DRIVE_ID de l'onglet CONFIG n'est lue par aucun code — documenté pour éviter de chercher.
  • Les échéances du calendrier : renouveler le jeton GitHub avant la mi-octobre 2026 ; régénérer l'index des tarifs vers mars 2027 ; et après la démonstration du 4 septembre, dérouler le nettoyage (onglets 2027 de test, fichiers de test du Drive, réglages de campagne et d'adresse de test des mails, puis un diagnostic de contrôle).
